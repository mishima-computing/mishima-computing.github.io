# ADR 0001: 共通ヘッダー・フッターの静的HTML管理（JS動的生成の不採用）

## 1. 背景と課題 (Context)
全HTMLページに共通するナビゲーション（ヘッダー・フッター）の管理は、静的サイトにおいてメンテナンスコストの課題となります。
通常のモダンWebフロントエンド開発では、`header.js`のようなスクリプトによるDOMの動的注入、もしくはSSG（Static Site Generator）を用いたビルドプロセスを採用し、「DRY（Don't Repeat Yourself）の原則」を守るのが定石です。
しかし、本プロジェクトでは、あえて各HTMLファイルにベタ書き（ハードコード）で共通パーツを複製配置する「泥臭い」手法を採用し、同期漏れのリスクはQAチェックリスト（運用プロセス）でカバーするアプローチを取りました。

## 2. 決定事項 (Decision)
**「JavaScriptによるナビゲーションの動的生成を行わず、全ページでHTMLを静的にハードコードする」**

## 3. 理由 (Rationale)
三嶋電算のコーポレートサイトにおける最重要ミッションは**「AI検索エージェントやシンプルなクローラーに対して、自社の事業内容と情報構造を完全に伝えること（Agent Readiness）」**です。

- JavaScriptによるDOM注入を採用した場合、JavaScriptを実行しない軽量なクローラーや一部のAIエージェントからは、ヘッダーのリンク群（サイト内の回遊導線）が一切見えなくなります。
- その結果、各ページが「孤立したページ（Orphan Pages）」と判定され、サイト全体のクローラビリティやエンティティSEO（企業情報の構造把握）に致命的な悪影響を及ぼすリスクがあります。
- 「DRY原則による開発者の利便性（ページごとに変わるのはダサいというエンジニア的感覚）」よりも、**「機械可読性の最大化（エージェントに自社を正しく認識させること）」**を戦略的に優先しました。

## 4. 結果 (Consequences)
- **Positive**: どんなクローラーやLLMエージェントであっても、サイト内の全リンクを辿り、情報構造を100%正確に把握できるようになりました。
- **Negative**: メニュー項目を1つ追加・変更するだけで、全HTMLファイルを修正する手間（コピペの手間）が発生します。
- **Mitigation**: この運用負荷と同期漏れリスクを軽減するため、`.github/PULL_REQUEST_TEMPLATE.md` および `QA_CHECKLIST.md` に「共通パーツ同期 (Header/Footer Sync)」の項目を必須確認事項として追加し、ヒューマンエラーをプロセスで防ぐ体制を構築しました。
